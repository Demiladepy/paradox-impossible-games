## D-001 — React + TypeScript + Vite + React Three Fiber + Rapier
**Status:** proposed · 2026-11-12

Verified available versions (checked against npm on 2026-11-12):

| Package | Version | Peer requirement |
| --- | --- | --- |
| react / react-dom | 19.3.1 | fiber needs `>=19 <19.4` ✔ |
| three | 0.187.0 | fiber needs `>=0.156` ✔ |
| @react-three/fiber | 9.8.2 | — |
| @react-three/drei | 10.7.9 | fiber `^9.0.0` ✔ |
| @react-three/rapier | 2.2.0 | fiber `^9.0.4`, react `^19` ✔ |
| zod | 4.6.7 | — |
| vite | 8.3.8 | — |
| typescript | 7.0.2 | — |

The set is mutually consistent. Node 22.20.0 / npm 11.6.2 on the build machine.

**Why R3F over bare Three.js:** drei gives us `useGLTF`, `useAnimations`, `Environment`,
`OrbitControls`, `Html` for free — each is a half-day we do not have. `@react-three/rapier`
makes gravity a reactive prop on `<Physics gravity={...}>`, which is exactly the primitive
Round 2 needs.

**Cost:** React reconciliation sits between us and the scene graph. Mitigation: all per-frame
mutation happens in `useFrame` against refs, never through `setState`.

**Risk flagged:** TypeScript 7 and Vite 8 are recent majors. If either fights the R3F
toolchain in the first hour of setup, drop to the previous major immediately — this is a
hackathon, not a chance to be early.

**Reversible:** the `game/` layer is plain TypeScript and does not depend on React.

## D-002 — Lux3D is a build-time asset pipeline, not a runtime service
**Status:** proposed · 2026-11-12

Result URLs from the Lux3D API expire after **2 hours** (documented). Generation is async and
takes an unknown but non-trivial time. Therefore assets are generated by a Node CLI, downloaded,
and committed under `public/assets/generated/` with a `manifest.json` recording prompt, version,
task id and date.

**Consequences:** the API key never reaches the browser; no backend is needed for Lux3D; the
demo cannot be broken by API latency, quota or an outage; the manifest doubles as the asset
iteration evidence the project report requires.

**Cost:** assets are frozen at build time. Acceptable — the *challenges* vary per run, not
the models.

---

## D-003 — The LLM returns data, never code; runtime stays deterministic
**Status:** proposed · 2026-11-12

Challenge generation produces a `ChallengeConfig` JSON validated by zod. The engine owns
physics, collisions, timers, scoring and win/loss. No `eval`, no `new Function`, no generated
expressions. Unknown rule types are rejected rather than ignored.

## D-004 — Solvability is verified by a headless simulation probe, and described honestly
**Status:** proposed · 2026-11-12

We run the real rule engine headless with a scripted agent on a waypoint graph. Passing means
"an agent completed it", not "the challenge is provably solvable". Wording in the UI, the
README and the report will say exactly that.

## D-005 — Third-person camera
**Status:** RESOLVED · 2026-11-14 · decided at the Milestone 2 deadline, as planned

Round 1 ("platforms are solid only when you are *not* looking at them") is close to unplayable
in first person: the player must walk where they cannot see, which reads as a broken control
scheme rather than a clever rule, and tends to induce motion sickness.

In third person the gaze direction becomes a deliberate, visible input the player aims — and,
critically, the Lux3D-generated contestant is **on screen the whole time**, which is worth real
points under the 30% "use of Manycore tools" criterion and makes a far better demo video.

**Resolution, with the mechanic built and running:** third-person, and the reasoning is now
evidence rather than prediction.

1. **The False Floor needs an aimable gaze.** In third person the view cone is something you
   steer independently of where you are walking: you can angle the camera so a platform sits
   just outside the cone, keeping it solid, while still seeing your route. First person welds
   gaze to heading, so "look away to cross" literally means crossing blind.
2. **Gravity inversion has to be legible on your own body.** When `upSign` flips, the
   contestant rotates and stands on the ceiling. In first person the only cue is that the world
   turned over, which is disorienting in the unhelpful way.
3. **The Lux3D contestant stays on screen the whole time**, which is worth real marks under the
   30% tooling criterion and makes a far better demo video.

Both modes stay implemented behind `CameraRig` and `V` still toggles them — first person is a
good way to feel how hostile the mechanic is, and costs nothing to keep. Third person is the
default and the one the demo is designed around.

## D-006 — Generation runs server-side; the game is complete without it
**Status:** RESOLVED · 2026-11-15

To call an LLM at runtime without exposing a key, we need one server-side route. Options:

1. Deploy to Vercel/Netlify with a single function. Clean; also gives us the "working demo link"
   the submission asks for. **Recommended.**
2. Vite dev-server middleware only — works for a recorded demo, not for a public link.
3. Ship a pack of pre-generated, pre-validated challenges and no live call.

Decision: build (3) first because it makes the game complete on its own, then add (1).
Either way, the game never breaks when the AI is unavailable.

## D-007 — Generated assets need a texture budget, not just a face-count budget
**Status:** accepted (measured) · 2026-11-12

First real generation, Lux3D task `6929533`, `G1-Turbo`, `faceCount: 20000`:

```
platform-slab.glb  12.95 MB
  meshes=1 primitives=1 materials=1  skins=0 animations=0
  textures=2 totalling 12.11 MB (93% of the file)
    [0] image 2048x2048 image/png 7.44 MB
    [1] image 2048x2048 image/png 4.67 MB
```

The mesh arrived at **18,272 triangles** — `faceCount` works and is worth setting. But geometry
is 7% of the payload. Lux3D returns 2K PNG PBR maps, and at ~12 MB per asset a six-asset arena
is a 70 MB download and a lot of GPU memory.

**Decision:** the asset pipeline gets a post-download optimisation pass before Milestone 1 ends —
resize textures (1024 for hero assets, 512 for background props) and re-encode PNG to WebP.
Expect roughly 10–20x off the file. `npm run inspect:asset` is the measuring tool and the
before/after numbers go straight into the project report, where asset iteration is explicitly
part of the rubric.

**Not doing:** KTX2/Basis. Better for GPU memory, but it needs native tooling and we do not have
the days to spend on it.

## D-008 — `aiPredictSize` guesses real-world scale, which is wrong for arena geometry
**Status:** accepted (measured) · 2026-11-12

The same slab came back with a longest side of **0.30 units**. `aiPredictSize: true` reasoned
about a real "floor tile" and sized it at ~30 cm. Arena platforms need to be metres across.

**Decision:** for arena and gameplay geometry, pass `customSize` (height in millimetres) instead
of relying on prediction, and normalise scale on load against the collider dimensions the game
defines. Prediction stays on for props where real-world scale is actually what we want.

## D-009 — Retargeted clips are renamed positionally on download
**Status:** accepted (measured) · 2026-11-12

Lux3D retargeting returns clips named `animation_1` … `animation_N`, not the animation IDs
that were requested. Game code must not depend on positional aliases, so `gen:character`
rewrites the names into the GLB at download time (`scripts/lux3d/glb.ts`), and
`npm run relabel:clips -- <entry>` applies the same fix to an asset generated earlier.

**Why positional order is trusted.** Clip durations from task `6929908`, against the order the
IDs were sent in:

| # | Requested ID | Duration |
| --- | --- | --- |
| 1 | Idle_Loop | 2.50s |
| 2 | Walk_Loop | 1.33s |
| 3 | Jog_Fwd_Loop | 0.93s |
| 4 | Sprint_Loop | 0.67s |
| 5 | Jump_Start | 1.33s |
| 6 | Jump_Loop | 2.50s |
| 7 | Jump_Land | 1.27s |
| 8 | Roll | 1.47s |
| 9 | Hit_Knockback | 0.83s |
| 10 | Death01 | 2.40s |

The locomotion triple is the tell: walk 1.33s > jog 0.93s > sprint 0.67s, cycle length falling
monotonically as gait speed rises, exactly as animation data should. Idle and Death are the two
longest. This is strong evidence, not proof — so `renameAnimations` refuses to rename at all
when the clip count and the delivered-ID count disagree, because a mislabelled clip is worse
than an honest `animation_N`.

**Still to confirm by eye:** that each renamed clip looks like its name when played. Pending —
the browser pane was unavailable at the time of writing.

## D-010 — Ship the animation GLB; keep the rigged GLB as the rig master
**Status:** accepted (measured) · 2026-11-12

The combined retarget output is **self-contained**: `meshes=1 skins=1 animations=10`. It carries
the skinned mesh, the skeleton and every clip, so the game loads one file and the separate
20.31 MB rigged GLB never needs to reach the browser.

Keep the rigged file in the repo anyway: it is our only copy of the rig, because the Lux3D URL
it came from expired two hours after generation. Note the consequence — **retargeting further
animations onto this character later needs a publicly reachable URL for `rigModelUrl`**, so the
rigged GLB would first have to go through the Aholo asset upload API. Budget for that before
asking for a second batch of clips, or request all needed clips in one task (max 10).

## D-011 — Raw Rapier, not `@react-three/rapier`
**Status:** accepted · 2026-11-13 · supersedes the physics row of D-001

`@react-three/rapier` binds the physics world to the React tree. The Milestone 3
solvability probe has to run the real simulation headless in Node, as fast as it can, with
no renderer — a React-bound world cannot do that, and discovering it in Milestone 3 would
mean rewriting movement and collision at the worst possible moment.

So `src/game/physics/world.ts` wraps `@dimforge/rapier3d-compat` directly and the view
layer copies transforms onto three.js objects once per frame.

**Cost:** we write the character controller glue ourselves (Rapier's
`KinematicCharacterController` does the hard part). **Benefit, already realised:**
`src/game/GameWorld.test.ts` drives a full arena in plain Node — determinism, falling,
winning, collider toggling — with no DOM and no GL context. That test file *is* the probe's
foundation.

## D-012 — Rapier is loaded as a separate chunk
**Status:** accepted (measured) · 2026-11-13

`rapier3d-compat` inlines its WASM as base64. Importing it statically put the whole thing
in the main bundle:

| | main bundle | lazy chunk |
| --- | --- | --- |
| static import | 5,597 kB (2,019 kB gzip) | — |
| dynamic import | 1,265 kB (350 kB gzip) | 4,335 kB rapier |

`initPhysics()` does the dynamic import, so the shell and the Asset Lab load without
paying for physics at all, and the arena fetches it while the title overlay is up.

## D-013 — Level geometry is verified against ballistics, not authored by eye
**Status:** accepted · 2026-11-14

`src/game/arena/reach.ts` computes, from the real tuning values, whether each hop on an
arena's route is actually makeable: closed-form jump ballistics, edge-to-edge AABB gaps,
and the rise between surfaces. `npm run analyze:arena` prints it; tests assert it.

Three classes of defect this now catches, all of which were present in ARENA_01 and none
of which fail loudly at runtime:

1. **Unreachable or sprint-only hops.** A gap the designer can clear because they know the
   route, and nobody else can.
2. **Wedge gaps** (`wedgeGaps`). A gap narrower than the player's body leaves the capsule
   resting on both lips: holding forward does nothing. It reads as broken controls, not as
   "jump here". ARENA_01's very first gap was 0.50 m against a 0.72 m body.
3. **Spawn penetration** (`spawnClearance`). Spawning the capsule inside the floor makes
   Rapier's character controller spend its steps resolving the overlap rather than moving.
   The player crept at roughly 0.3 m/s for the first thirty seconds. This is the one that
   cost the most to find, and it is now a one-line assertion.

The ascent was then rebuilt as a staircase with zero gaps and even 1.0 m rises. PARADOX
should be difficult because its rules are strange, not because its geometry demands
precision platforming — the arena is the stage for the mechanic, not the challenge itself.

## D-014 — The autopilot is the solvability probe, arriving early
**Status:** accepted · 2026-11-14

`src/game/agent/autopilot.ts` follows an arena's authored route, aims at the next platform,
sprints only when the reach analysis says walking cannot clear the gap, and jumps when it
runs out of floor or stops making progress. `autopilot.test.ts` drives it from spawn to
exit in plain Node and asserts the run is won, is reproducible, and finishes in a sensible
time.

Today it is the end-to-end test: it exercises arena data, Rapier collision, the character
controller, jump ballistics, the camera basis movement is expressed in, and the objective
check, in one pass, with no browser. In Milestone 3 it becomes the thing that decides
whether an AI-proposed challenge is fair before a player is allowed in.

Note what it is not: completing a run proves *an agent completed this configuration*. It is
not a proof that every configuration is winnable, and we will not describe it as one.

## D-015 — Rules are modules with a parse step, and loading is all-or-nothing
**Status:** accepted · 2026-11-14

`RuleModule.parse(rule, arena)` returns either typed parameters or a message explaining the
refusal. The engine parses every rule in a set before applying any of them, so a failure
late in the list cannot leave earlier rules half-installed — a player would otherwise be
dropped into a world that does not match its own briefing.

This parse step is where Milestone 3's challenge validation will live. It already checks
the things a generated rule gets wrong: target ids that do not exist, targets that are not
platforms (the exit is a trigger volume with no collider to switch off), triggers the
module does not implement, parameters out of range or of the wrong type, duplicate rule
ids, and semantic contradictions such as a gravity warning longer than its own interval.

`SPATIAL_PORTAL` is declared in the type union and deliberately unimplemented. A challenge
requesting it is **refused with a reason**, never silently ignored.

## D-016 — Two details that turn CONDITIONAL_PLATFORM from a gimmick into a mechanic
**Status:** accepted · 2026-11-14

**Hysteresis.** A single dot-product threshold makes a platform at the edge of the view
cone flicker many times a second as the camera breathes — the floor buzzing in and out of
existence. The angle at which a platform becomes observed is narrower than the angle at
which it stops being observed, so it latches. A test wobbles the camera on the cone
boundary for three seconds and asserts at most two transitions.

**The supporting platform is exempt.** A rule that deletes the ground under your feet the
instant you glance down is a punishment, not a puzzle — and in third person the camera
looks over the player at exactly the platform they are standing on. You can unmake the
floor ahead of you, never the floor beneath you.

## D-017 — Gravity inverts along Y only, instantly, with a countdown
**Status:** accepted · 2026-11-14

Stated plainly so the report does not overclaim: `GRAVITY_DIRECTION` flips "down" between
-Y and +Y. It does **not** support arbitrary gravity directions. Walking on walls needs the
character controller re-based onto an arbitrary axis, which is not a thing to attempt four
days from a deadline.

The flip is instantaneous after a visible countdown. An eased transition through zero was
considered and rejected: it leaves the player floating with no control authority and no
clear moment of change, and it creates a window where the gravity vector is near zero that
every "which way is up" calculation then has to special-case.

Arena 02's ceiling is **continuous** across the whole corridor. An earlier version had
ceiling only above the floor gaps, which meant inverting while standing on a floor island
threw the player into the sky with nothing to land on. Inverting must always be survivable;
the danger belongs in the *return*, which is on a schedule you can see and plan around.

## D-018 — Four validation gates, cheapest first, and the probe runs last
**Status:** accepted · 2026-11-15

`validateChallenge` runs **shape** (zod, `.strict()` so an unexpected key is a rejection
rather than a silent drop) → **references** (every arena, platform and exit it names must
exist; unimplemented rule types refused) → **sanity** (internal coherence: contradictory
gaze rules, two gravity schedules, inverting gravity in an arena with no ceiling, duplicate
ids) → **solvability** (play it).

The first three are microseconds and catch most of what a model gets wrong. The probe costs
a few hundred milliseconds because it runs the real simulation, so it only runs on a
challenge that has already earned it.

Generation happens **server-side** and validates before replying, so a challenge that
reaches the browser has already been played by an agent. A rejection is fed back to the
model as a specific reason with one retry; after that the fallback pack is used and the UI
says so. The key never leaves the server (`server/challenge-handler.ts`, mounted at
`/api/challenge`).

## D-019 — The probe plays the mechanics, and a naive-agent control proves they bite
**Status:** accepted · 2026-11-15

A probe that ignores the rules would pass every challenge and mean nothing. The agent reads
the active rules: under THE FALSE FLOOR it averts its gaze from the platform it is crossing
to and strafes, under OBJECT_STATE it waits for the floor to come back, and it refuses to
step into a gap no jump can clear.

Every challenge is therefore probed **twice** — once by an agent that knows the rules and
once by one that does not. If both succeed, the rule is inert and the round is not actually
a challenge. That control test is what caught the next two entries.

### What the control test found

**The exemption was rescuing the player mid-fall.** The "never unmake the floor under your
feet" exemption used a purely geometric test, which counts a platform as supporting the
moment the feet pass within a third of a metre — during a fall, that is the instant before
landing. The platform you were staring at quietly turned solid and caught you, so the naive
agent cleared the course in the same 9.5s as the rule-aware one. Gating on `grounded`
instead stuttered (it is a character-controller output that flickers false for a step as the
player settles, which was enough to unmake the ground beneath them). Vertical speed says it
properly: at rest the player carries the small downward bias, while a jump lands several
times faster.

**Gaze had to move from the camera to the character's head.** Measuring the view cone from
the camera eye seemed more honest — "what is on screen" — and made the mechanic unplayable
in third person. A third-person camera's whole job is to frame the player, so the ground
immediately beside them is always in shot; turning away swings the camera round and keeps
looking at the same patch of floor. There is no yaw that clears the platform you are about
to step onto. Measured from the character's head, turning away does what it says, and it
behaves identically in both camera modes.

Neither bug would fail a type check, and neither throws. Both were found by asking a dumb
agent to try.

## D-020 — What "verified playable" is allowed to mean
**Status:** accepted · 2026-11-15

A passing probe means: *an agent completed this configuration, in this simulation, with
this seed.* It is an existence proof by construction.

It is **not** a proof that the challenge is solvable in general, and it is **not** a claim
that a human would find it fair or discoverable — the agent is handed the route from the
arena data, where a player has to deduce it. The briefing screen says exactly this
("an agent completed this round in 9.5s — that is not a proof it is winnable for everyone")
and the project report will say the same.

A failing probe is the stronger result and the one that earns its keep: nobody gets sent
into a round that could not be finished.
